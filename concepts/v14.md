# Concept: v14, a clean restructuring

Status: **Approved, in implementation** · Date: 2026-11-06 · Scope: `codebar-ag/laravel-microsoft-entra-sso`, release **v14.0**

v14 is allowed to break everything. This document records what is wrong with v13.16 (found by reading all of `src/`), the target
structure, the decisions, and how the work is cut into reviewable pull requests. Approved by the maintainer; implementation follows the delivery plan in section 8 as a stack of pull requests on the long-lived `v14` branch.

## 1. Goal

A small, strict, boring package: sign a person in with Microsoft Entra ID (single directory or customer directories), validate
the tokens, decide through explicit extension points who may get in and which local user they become, and offer a typed Graph
client. Enterprise level means: immutable typed objects instead of arrays, one place for every rule, no shared mutable state, no
legacy shims, fail-fast configuration, maximum static analysis, and tests that document behaviour.

**Non-goals:** other identity providers, an Socialite-like multi-driver API, shipping UI that depends on a CSS framework, support
for PHP below 8.5 or Laravel below 13.

## 2. Review of v13.16 (facts from the code)

| # | Finding | Evidence | Consequence |
| --- | --- | --- | --- |
| 1 | **No `declare(strict_types=1)` in any of the 28 source files, none of the 23 classes is `final`** | `grep` over `src/` | Silent coercion, every class is an extension point by accident |
| 2 | **Factory, Manager and "driver" for a single driver** | `Contracts\Factory`, `MicrosoftEntraSSOManager::driver()` throws for anything but `'microsoft'` | Three indirections (facade, factory, provider) that carry no behaviour; a Socialite imitation |
| 3 | **`config()` is read everywhere** (controllers, services, middleware, policy, validator, model), each time with defensive `is_array`/`is_numeric` juggling | ~40 call sites | Configuration is validated lazily, per request, in different ways; an invalid value fails late or is silently replaced by a default |
| 4 | **The sign-in rules exist three times**: `HandlesMicrosoftSSO::findOrRegisterUser`, the default `HasMicrosoftSSO::findOrCreateFromMicrosoft`, and every app that overrides it (Pingu does) | Same find-by-id, find-by-email, link, register sequence in all three | Behaviour drifts; the linking policy has to be remembered by every override (the README says so) |
| 5 | **Business logic lives in a controller trait and in a model trait** | `HandlesMicrosoftSSO` (160 lines), `HasMicrosoftSSO` (197 lines) | Not unit-testable without HTTP or a model; the model trait is also the extension mechanism |
| 6 | **`MicrosoftOAuthService` is a singleton with mutable per-request state** (`setRedirectUri()`, `stateless()`), and does URL building, token exchange, refresh, `/me`, id-token orchestration, retry setup and redirect validation | 334 lines; the token-error block is copied between exchange and refresh | Concurrency hazard under Octane/queues; too many reasons to change |
| 7 | **Arrays are the data model**: `findOrCreateFromMicrosoft(array)`, `linkMicrosoftAccount(array)`, `SSOUser::toArray()`, `getUserProfile(): array`; `SSOUser` has 12 constructor arguments and three near-identical `with*()` copy methods | `Data/SSOUser`, trait, Graph service | Stringly-typed keys (`'tenant_id'`, `'object_id'`) as the public API; no compile-time safety |
| 8 | **Session state under five magic string keys**, written and read in two controllers | `microsoft_entra_sso_state`, `_code_verifier`, `_guard`, `_issued_at`, `_nonce` | Easy to leave half-cleared; no single owner |
| 9 | **Runtime schema sniffing** (`supportsTenantColumn()` with a static cache and `Schema::hasColumn`) | `Models/MicrosoftSSOIdentity` | A backwards-compatibility hack in the hot path; two code paths to test |
| 10 | **`SSOException` is a god class** with 14 named constructors, mixed translated and hard-coded English messages | `Exceptions/SSOException` | Callers cannot catch by meaning; user-facing and developer-facing messages are mixed |
| 11 | **The `Provider` interface does not match its implementation** (`getAuthorizationUrl` has an extra optional `$nonce` only on the class) | `Contracts/Provider` vs `MicrosoftOAuthService` | The nonce cannot be used through the contract |
| 12 | **Static analysis is weakened**: level 9 (max is 10), only `src/`, `treatPhpDocTypesAsCertain: false`, an ignore rule | `phpstan.neon.dist` | Tests and a class of errors are not analysed |
| 13 | **Insecure defaults**: `email_linking = always`, `auto_register = true`, default scopes include `GroupMember.Read.All` (needs admin consent in every customer directory) | `config/microsoft-entra-sso.php` | Safe only for a single, trusted directory; the multi-tenant risk (nOAuth) needs opt-in protection |
| 14 | **UI shipped with the package** depends on Tailwind classes; the login error flash key and login route are hard-wired | `resources/views/*`, `redirectToLoginWithError` | Unusable as is in an Inertia/Vue app (Pingu) |
| 15 | **Controllers catch `\Throwable`** and answer with a generic message; logging is done inline | `HandleMicrosoftCallbackController` | Real bugs are reported as sign-in failures |

What is good and stays: PKCE with S256, state with TTL, the validated id token (RS256, JWKS cache with a refresh cooldown, `aud`,
`iss`, `tid`, `exp/nbf/iat`, nonce), `tid`/`oid` identity, the login gate, email-linking modes, encrypted token storage, the Graph
refresh with a cache lock, and the events.

## 3. Target structure

```
src/
  EntraSsoServiceProvider.php          boots config, routes, migrations, translations; binds the objects below
  Config/
    EntraConfig.php                    final readonly, built and validated ONCE from config('microsoft-entra-sso')
    GuardConfig.php                    final readonly: guard name, user model, redirect_after_login
  Identity/                            immutable value objects
    EntraIdentity.php                  tenantId (Guid), objectId (Guid): the stable identity of a person
    Profile.php                        name, email, jobTitle, department
    Tokens.php                         access, refresh, expiresAt, scopes, idToken
    SignIn.php                         EntraIdentity + Profile + Tokens (what the app receives)
  Flow/                                the sign-in, as small single-purpose classes
    FlowState.php + FlowStateStore.php one session key; state, PKCE verifier, nonce, guard, issuedAt; pull() validates TTL
    StartSignIn.php                    action: builds the authorization request, stores FlowState
    CompleteSignIn.php                 action: state check, code exchange, id token, gate, resolve user, login
    ResolveUser.php                    action: the ONE place for find-by-identity / link / register
    EmailLinkingMode.php               enum: Always | SameTenantOnly | Never
    DenialReason.php                   enum: LoginGate | EmailLinkingDisabled | EmailLinkingTenantMismatch | TenantMismatch | ...
  Contracts/
    LoginGate.php                      allows(SignIn, GuardConfig): bool          (kept, typed)
    UserProvisioner.php                create(SignIn): Authenticatable            (replaces overriding findOrCreateFromMicrosoft)
    SsoUser.php                        the user model contract: microsoftIdentity(), isMicrosoftTokenExpired()
  Clients/                             all HTTP, all stateless, all take EntraConfig
    TokenClient.php                    exchangeCode(), refresh(): Tokens   (one error mapper, one retry policy)
    GraphClient.php                    get/paginate with token + retry; used by Profile lookup and the Graph helper
    JwksClient.php                     fetch + cache of signing keys
    IdTokenValidator.php               validate(string, nonce): IdTokenClaims
  Graph/
    GraphProfileService.php            typed GraphProfile, groups, photo, group membership (cached), refresh with lock
  Http/
    Controllers/RedirectToMicrosoftController.php   invokable, final, 5 lines
    Controllers/HandleMicrosoftCallbackController.php   invokable, final, delegates to CompleteSignIn
    Middleware/EnsureSsoEnabled.php
    Requests/CallbackRequest.php       validated code / state / error input
  Models/MicrosoftIdentity.php         table microsoft_sso_identities (unchanged), typed attributes
  Concerns/HasMicrosoftIdentity.php    the model trait: relation + isLinked/unlink/isTokenExpired. NO sign-in logic
  Events/                              SignedIn, UserRegistered, SignInDenied (final readonly, no tokens in denied)
  Exceptions/                          ConfigurationException, InvalidStateException, TokenException, InvalidIdTokenException,
                                       SignInDeniedException(reason: DenialReason), GraphException
```

Rules for every class: `declare(strict_types=1)`, `final` (the extension points are the contracts, not subclassing), constructor
injection of `EntraConfig` instead of `config()`, no static state, no arrays crossing a public boundary where a value object fits.
PHP 8.5 features are used where they remove code (`clone` with property overrides replaces the `with*()` copy methods).

## 4. The sign-in, as designed

1. `StartSignIn`: validate the guard, create a `FlowState` (state, PKCE verifier, nonce, guard, `issuedAt`), store it under one
   session key, return the authorization URL (immutable request object; the redirect URI is derived per request, never stored on a
   singleton).
2. `CompleteSignIn`: `FlowStateStore::pull()` (guard and TTL checked, the state is consumed), reject `error=` callbacks, exchange
   the code (`TokenClient`), fetch the profile (`GraphClient`), validate the id token (`IdTokenValidator`), build a `SignIn`.
3. **Gate**: `LoginGate::allows(SignIn, GuardConfig)` runs before anything is looked up, linked or created.
4. `ResolveUser`:
   1. find by `EntraIdentity` (`tid`, `oid`); a known identity from another tenant is refused;
   2. else apply `EmailLinkingMode` to an existing user with the same email (`Never` refuses, `SameTenantOnly` requires the same
      stored `tid`, `Always` links);
   3. else, if `auto_register`, call `UserProvisioner::create(SignIn)`; the package creates the identity row and dispatches
      `UserRegistered`.
5. Log the user in, regenerate the session, clear the flow state, dispatch `SignedIn`, redirect.

The model never contains sign-in logic. An app customises exactly two things through contracts: **who may enter** (`LoginGate`)
and **how a new user is created** (`UserProvisioner`).

## 5. Configuration (fail fast)

- `EntraConfig` is built once (in the container binding) from `config('microsoft-entra-sso')` and validated: tenant authority
  (GUID, `organizations`, `common` or `consumers`), client id/secret, redirect host allowlist, scopes, `EmailLinkingMode`, gate
  class (must exist and implement the contract), guards (model must exist and implement `SsoUser`). An invalid value throws
  `ConfigurationException` on first use, with the key in the message, never a silent default.
- **Secure defaults** (decision V3): `email_linking = never` unless `tenant_id` is a single directory GUID, where `always` is
  allowed; `organizations`/`common` with `always` is a configuration error. `auto_register = false`. Default scopes
  `openid profile email User.Read`. `id_token.require = true`.
- The identity table keeps its name and shape (`entra_tenant_id` becomes part of the create migration for new installs; the
  second migration stays as the upgrade path for v13 databases). No runtime schema sniffing.

## 6. Quality bar

- PHPStan **max** (level 10) over `src/` **and** `tests/`, no `ignoreErrors`, no baseline, `treatPhpDocTypesAsCertain` default.
- Pest type coverage 100 %, line coverage minimum 95 %, architecture tests: strict types, `final`, no `config()` outside the
  config object and the service provider, no `Facade` use inside `src/` except the facade itself, `Clients` never touch the
  session, `Flow` never touches HTTP.
- Pint (laravel preset plus `declare_strict_types`), `composer audit`, dependency review (existing workflows).
- Tests are rewritten around the new units (one test file per class, a `FakeEntra` for the OAuth/Graph/JWKS HTTP).
- PHP `^8.5`, Laravel `^13`, one CI job (PHP 8.5), prefer-lowest and prefer-stable.

## 7. Breaking changes (what the v14 upgrade guide must say)

| v13 | v14 |
| --- | --- |
| `HasMicrosoftSSO` trait with `findOrCreateFromMicrosoft`, `linkMicrosoftAccount`, `updateMicrosoftTokens` | `HasMicrosoftIdentity` (relation and helpers only). User creation moves to a `UserProvisioner` |
| `SSOAuthenticatable` interface | `SsoUser` interface (smaller) |
| `array $microsoftUser` everywhere, `SSOUser::toArray()` | typed `SignIn` / `EntraIdentity` / `Profile` / `Tokens` |
| `MicrosoftEntraSSO::driver('microsoft')`, `Factory`, `Provider`, `Manager` | removed; inject `StartSignIn`/`CompleteSignIn` or use the facade for `graph()` |
| `config('microsoft-entra-sso.*')` keys read ad hoc | same file, validated once; some defaults change (section 5) |
| `SSOException` with many constructors | focused exceptions; `SignInDeniedException::$reason` is a `DenialReason` enum |
| Events `SSOUserAuthenticated`, `SSOUserRegistered`, `SSOLoginDenied` | `SignedIn`, `UserRegistered`, `SignInDenied` (typed payloads) |
| Blade components and error view with Tailwind classes | removed from the package; apps render their own (Pingu already does); the flash key stays configurable |
| PHP 8.3 to 8.5 | PHP 8.5 only |

## 8. Delivery plan (each step is a PR, merged after review)

| PR | Content | Done when |
| --- | --- | --- |
| **1: Foundations** | `EntraConfig`/`GuardConfig` with validation, `declare(strict_types=1)` and `final` everywhere (mechanical), PHPStan max over `src` and `tests`, arch tests, secure defaults | All existing tests still pass or are migrated; analysis at max |
| **2: Value objects and clients** | `Identity/*`, `Tokens`, `TokenClient`, `GraphClient`, `JwksClient`, `IdTokenValidator` on the new config; the OAuth service is deleted | Clients covered by unit tests with `FakeEntra`; no `config()` outside the config object |
| **3: Flow** | `FlowState(+Store)`, `StartSignIn`, `CompleteSignIn`, `ResolveUser`, enums, focused exceptions, events, thin controllers; `HandlesMicrosoftSSO` and the Manager/Factory removed | Feature tests for redirect/callback pass; the sign-in rules exist exactly once |
| **4: Model side** | `HasMicrosoftIdentity`, `SsoUser`, `UserProvisioner`, `MicrosoftIdentity` model, migrations, schema sniffing removed | A fresh install and a v13 database both migrate and work |
| **5: Graph and cleanup** | `GraphProfileService` with typed results, remove Blade/Tailwind views, README rewrite, UPGRADE.md, release notes | README and upgrade guide match the code; v14.0.0 tag |

Release mechanics: the repository's release workflow tags a **minor** on every merged PR and requires an approving review on
`main`. v14 must be released as a **major**: the workflow needs a major bump for the final PR (or a manual tag), and the
intermediate PRs must not publish v13.x tags. Decision V5 below.

## 9. Decisions

| # | Topic | Decision |
| --- | --- | --- |
| V1 | Compatibility | None. v14 breaks the API, the model trait, events, exceptions and some config defaults. A written upgrade guide replaces shims |
| V2 | Extension model | Contracts only (`LoginGate`, `UserProvisioner`, `SsoUser`); every class is `final` |
| V3 | Defaults | Secure by default: `email_linking = never` for multi-directory authorities, `auto_register = false`, minimal scopes, id token required |
| V4 | UI | The package ships no UI. Messages are translatable keys; apps render them |
| V5 | Releases | Work lands on a long-lived branch `v14` (PRs target it, no tags); `v14` is merged to `main` once and tagged **v14.0.0** manually |
| V6 | Identity table | Same table and columns; `entra_tenant_id` in the create migration; the add-column migration remains as the v13 upgrade path |
| V7 | PHP / Laravel | PHP `^8.5`, Laravel `^13`, PHP 8.5 features used where they reduce code |

## 10. Open points (resolved)

1. **Dedicated `v14` branch: approved (V5).** Work lands on `v14`; pull requests target it (or the previous PR of the stack); no tags and
   no releases until `v14` is merged to `main` once and tagged **v14.0.0** manually.
2. **`Always` email linking: approved, restricted.** `email_linking = always` stays available only when `tenant_id` is a single
   directory GUID. `organizations`, `common` and `consumers` combined with `always` is a `ConfigurationException`.
3. **Pingu migrates after v14.0.** Pingu's `User::findOrCreateFromMicrosoft` override and `ProvisionMicrosoftSsoUserListener` become a
   `UserProvisioner` and a `SignedIn` listener; that happens in Pingu after v14.0 and is not part of this work.
